# SEO: публикация и проверка

## Подготовленные изменения

Сборка клиента создаёт отдельный HTML с уникальными title, description, canonical и Open Graph для 31 публичного маршрута. Sitemap автоматически собирается из того же списка, без вымышленных дат обновления. Тело страницы по-прежнему отрисовывает React: это не полный SSR/пререндеринг.

Organization и WebSite содержат реальное имя ИП, ИНН, юридический адрес из оферты и телефон из контактов. Юридический адрес не объявлен офисом для приёма клиентов. Часы работы не добавлены до уточнения: приём заявок формой, ответы менеджера и съёмки могут иметь разный режим.

Express перенаправляет /ckb и /vipiski (со слешем и без) на главную кодом 301. Неизвестные страницы получают HTTP 404, страницы авторизации — noindex. Подключены favicon.png и brand-logo.png, исправлены ссылки в PWA.

## Публикация

1. Проверить текущий конфиг Nginx и сохранить его копию. Выяснить, кто отдаёт HTML: Nginx или Express.
2. Собрать клиент: `npm ci`, затем `npm run build`. Публиковать весь client/dist, включая вложенные папки, favicon.png, brand-logo.png, sitemap.xml и 404.html.
3. Собрать сервер по действующей Linux-процедуре и перезапустить соответствующий процесс PM2. CLIENT_DIST_PATH при необходимости задаёт абсолютный путь к опубликованному клиенту.
4. Если Nginx сам отдаёт HTML, добавить в существующий HTTPS-блок точечные редиректы:

```nginx
location = /ckb { return 301 https://madewlove.ru/; }
location = /ckb/ { return 301 https://madewlove.ru/; }
location = /vipiski { return 301 https://madewlove.ru/; }
location = /vipiski/ { return 301 https://madewlove.ru/; }
```

Для статической отдачи try_files должен находить вложенные index.html. Неизвестные страницы должны возвращать 404 вместо безусловной отдачи главной с кодом 200. Сохранить API, загрузки и маршруты авторизации; для последних нужен noindex. Не заменять весь конфиг вслепую. Если HTML отдаёт Express, эти статусы уже предусмотрены кодом.

5. Проверить перенаправления HTTP и HTTPS www на https://madewlove.ru с сохранением пути и параметров. Для HTTPS www нужен действующий сертификат. Текущего конфига хостинга в репозитории нет.
6. Перед перезагрузкой Nginx выполнить `nginx -t`.

## Проверка после публикации

- /ckb, /ckb/, /vipiski: 301, в Location — главная.
- Главная, /contacts, /price/pregnancy: 200; уникальные title/description видны в исходном HTML без JavaScript; canonical соответствует странице.
- /favicon.png: 200, image/png, квадратное изображение.
- Случайный несуществующий адрес: 404.
- Sitemap и robots.txt доступны и используют основной HTTPS-домен без www.
- Проверить отрисованный контент в Search Console, запросить переобход главной и старых адресов. Не запрещать старые адреса через robots.txt: робот должен увидеть редирект.

## Проверено локально

Сборка клиента и TypeScript сервера прошли. Проверены 31 маршрут, уникальность заголовков/описаний, canonical/Open Graph, контакты в JSON-LD и sitemap. Временный локальный Express подтвердил ответы 301/200/404, noindex авторизации и доступность PNG-иконки. На работающем сайте изменения ещё не проверены и не опубликованы.

## Следующие шаги

Проверить статистику запросов, выбранные поисковиками canonical, отрисованный текст и мобильную скорость после публикации. При подтверждённых проблемах рендеринга внедрить полный SSR/пререндеринг. Улучшать страницы отдельных услуг и внешние подтверждения бренда на основе этих данных. Текущие технические исправления не доказывают причину низких позиций и не гарантируют рост.
